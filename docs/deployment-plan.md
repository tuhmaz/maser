# خطة البيئات والنشر

## مبدأ عام

يجب عدم التطوير مباشرة على بيئة الإنتاج.

## البيئات

### محلية
`localhost` — للتطوير والاختبارات الأولية.

### اختبار (Staging)
```
staging.alemedu.com
staging-api.alemedu.com
staging-admin.alemedu.com
```
تحتوي على: قاعدة بيانات منفصلة، حسابات تجريبية، محتوى غير حقيقي أو نسخة اختبارية، **بدون إرسال رسائل حقيقية للمستخدمين**.

### إنتاج
```
alemedu.com
api.alemedu.com
admin.alemedu.com
```

## قواعد صارمة بين البيئات

- لا تشارك البيئات نفس قاعدة البيانات
- لا تُستخدم مفاتيح الإنتاج في الاختبار
- لا تُنسخ بيانات الطلاب الحقيقية إلى بيئة التطوير
- تُحفظ الأسرار داخل ملفات بيئة مؤمَّنة أو مدير أسرار (secrets manager)، أبدًا في الكود
- لا تُرفع ملفات الأسرار إلى Git (`.env` مستثنى دائمًا عبر `.gitignore`)

## البنية التحتية (المرحلة الثالثة من التنفيذ)

**الأعمال:** إعداد DNS، إنشاء النطاقات الفرعية، إصدار شهادات SSL، إنشاء قواعد البيانات، إعداد مستخدم قاعدة البيانات، إعداد Redis، إعداد خدمات systemd، إعداد Nginx، إعداد النسخ الاحتياطي، إعداد سجلات التشغيل، إعداد المراقبة، إعداد عملية النشر.

**الخدمات المتوقعة (systemd):**
```
alemedu-api.service
alemedu-worker.service
alemedu-web.service
alemedu-admin.service
```
راجع [`infrastructure/systemd/`](../infrastructure/systemd).

**متطلبات النسخ الاحتياطي:** نسخة دورية من قاعدة البيانات، الاحتفاظ بعدة نسخ سابقة، اختبار الاستعادة فعليًا (وليس نظريًا فقط)، فصل نسخة الإنتاج عن نفس القرص عند الإمكان، توثيق خطوات الاستعادة.

**شرط قبول البنية التحتية:**
- جميع الخدمات تبدأ تلقائيًا بعد إعادة تشغيل الخادم
- فشل خدمة واحدة لا يكشف أسرار النظام
- يمكن الرجوع إلى إصدار سابق (rollback)
- يمكن استعادة قاعدة البيانات فعليًا
- بيئة الاختبار منفصلة تمامًا عن الإنتاج

## قبل النشر التجريبي (Staging → أول تجربة حقيقية)

مراجعة جميع الصلاحيات، اختبار إنشاء الحساب، اختبار الجلسات، اختبار استعادة كلمة المرور، اختبار جميع الدروس، مراجعة جميع الأسئلة، اختبار النسخ الاحتياطي، اختبار الاستعادة، تفعيل المراقبة، إعداد صفحة حالة وصيانة، إعداد وسائل التواصل والدعم، إنشاء حسابات تجريبية.

**جمهور الاختبار الأول:** مجموعة صغيرة من الطلاب، عدد محدود من أولياء الأمور، أشخاص يختبرون الهاتف والكمبيوتر، مراجع تعليمي، مسؤول دعم.

**ما يُراقَب:** أخطاء التسجيل، مشاكل الهاتف، الأسئلة غير الواضحة، مدة الاختبار، عدد المنسحبين، أخطاء الجلسة، المهام التي لا تُكمل، استفسارات المستخدمين.

## مراحل الإطلاق من موقع الإيمان (تدريجي عبر Feature Flag)

1. إعلان محدود في صفحات مرتبطة بالمادة التجريبية
2. بطاقة في الصفحة الرئيسية
3. إعلانات داخلية في المواد والصفوف المناسبة
4. رسائل للمستخدمين الذين وافقوا على استقبال التحديثات

**قاعدة مهمة:** لا يُرسَل جميع زوار موقع الإيمان إلى المنصة الجديدة منذ اليوم الأول. تُرفع نسبة العرض تدريجيًا حتى يمكن إيقاف الإعلان فورًا إذا ظهرت مشكلة.

## الأداء (اعتبارات النشر)

- **واجهة المستخدم:** تحميل تدريجي، ضغط الصور، تجنّب مكتبات كبيرة غير ضرورية، Server Rendered/Static للمحتوى العام، Client Components فقط عند الحاجة
- **الـ API:** فهارس قاعدة البيانات، Pagination، منع N+1 Queries، تخزين مؤقت للمناهج العامة، تنفيذ المهام الثقيلة في Worker منفصل، قياس الاستعلامات البطيئة، تحديد مهلات الطلبات (timeouts)
