# اختبارات Playwright E2E — Alemedu

اختبارات متصفح حقيقية (Chromium) تغطي المسارات الحرجة التي أُصلحت أو بُنيت
خلال هذه الجلسة — كل سيناريو هنا يترجم اختبارًا يدويًا عبر curl إلى اختبار
آلي دائم يمنع تكرار نفس الكسر مستقبلًا.

## المتطلبات قبل التشغيل

هذه الاختبارات تتصل بخدمات حقيقية شغّالة فعليًا، وليست معزولة (mock):

1. PostgreSQL (docker-compose) مع كل الترحيلات مطبَّقة (`scripts/migrate.sh up`).
2. `services/api` شغّال على المنفذ 8080 (`go run ./cmd/api`).
3. `apps/web` شغّال على المنفذ 3000 (`npm run dev --workspace=apps/web`).
4. `apps/admin` شغّال على المنفذ 3001 (`npm run dev --workspace=apps/admin`).
5. حساب أدمن بالبريد/كلمة المرور في `tests/support/admin.ts` موجود فعليًا
   (`scripts/create-admin.sh`).

## التشغيل

```bash
npm install
npx playwright install chromium   # مرة واحدة فقط
npm run e2e                       # من جذر المستودع
# أو من هذا المجلد مباشرة:
npx playwright test
```

## البنية

- `tests/web/` — اختبارات تطبيق الطالب (المنفذ 3000).
- `tests/admin/` — اختبارات لوحة الإدارة (المنفذ 3001).
- `tests/support/` — مساعدات مشتركة: تسجيل مستخدم عبر الـAPI (أسرع من قيادة
  النموذج لكل اختبار)، وتنفيذ SQL مباشر لحالات لا تصل إليها الواجهة (مثل
  تقديم موعد مراجعة خطأ للاختبار دون انتظار 24 ساعة فعليًا).

## ملاحظات مهمة

- **لا تشغيل متوازٍ** (`workers: 1`): كل الاختبارات تشترك في نفس قاعدة
  البيانات الحية، فتشغيلها بالتوازي قد يسبب تضاربًا في الحالة (سباقات على
  حدود معدل /auth/register مثلًا).
- **`/auth/register` محدود بـ20 طلبًا/دقيقة لكل IP** (حماية حقيقية مقصودة).
  إعادة تشغيل الحزمة كاملة عدة مرات بسرعة قد يصطدم بهذا الحد أحيانًا؛
  `apiRegister` في `support/api.ts` يعيد المحاولة تلقائيًا عند 429 بدل تعطيل
  الحماية نفسها.
- **بيانات الاختبار لا تُنظَّف تلقائيًا** — كل تشغيل ينشئ مستخدمين جددًا
  ببريد فريد (`uniqueEmail`) فلا تصادم، لكنهم يتراكمون في قاعدة بيانات
  التطوير. مقبول للتطوير المحلي، ويحتاج قاعدة بيانات نظيفة مُهاجَرة فقط
  (مثل CI) للنشر الحقيقي.
